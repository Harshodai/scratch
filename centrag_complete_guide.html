Foundations

CentRAG (Centralized RAG) is an enterprise-grade retrieval-augmented generation platform designed to serve multiple teams from a single, multi-tenant, pluggable architecture. It exists because most organizations end up with many ad-hoc LLM integrations — each team rolling their own embedding pipeline, their own prompt layer, their own connectors. CentRAG replaces that chaos with one governed platform: consistent quality, shared cost, unified observability.

The core innovation is that it treats retrieval as a routed, agentic decision rather than a static "always embed and search" pipeline. Different query types get different retrieval strategies — SQL for structured data, graph traversal for entity-rich domains, BM25/structural for documents — all driven by a LangGraph-based orchestrator.

Corrective RAG (CRAG) adds a retrieval evaluator that grades context quality after any retrieval step. If the result is "Incorrect" or "Ambiguous," it triggers a correction: web search, broader window, or a disambiguation question. It's a quality guardrail, not a retrieval method.

Agentic RAG wraps retrieval in an agent that plans and routes. Instead of always using the vector store, the agent decides which tools to call — SQL, log filters, graph queries, vector search — based on query type. CentRAG's SIMPLE/STANDARD/COMPLEX/RESEARCH routing is an Agentic RAG pattern.

Graph RAG builds and queries a knowledge graph (e.g. Neptune/Neo4j) to handle multi-hop reasoning — "who owns service X and what incidents affected its dependencies?" It's a retrieval backend, not an orchestration layer.

These three are orthogonal and complementary. CRAG wraps any retrieval. Agentic RAG routes between retrievers. GraphRAG is one retriever among many. CentRAG uses all three simultaneously.

Model Context Protocol (MCP) is an open standard by Anthropic that exposes external systems (databases, logs, ticketing tools, memory backends) as uniform JSON-RPC tool endpoints that any MCP-aware agent framework can call.

CentRAG adopts MCP because it eliminates bespoke per-system integrations. Instead of writing a custom GOS DB connector, a custom Jira connector, etc., you write one MCP server per system and any agent — including future ones — can use it. Governance becomes: "enable/disable an MCP server for a team."

Think of RAG as the knowledge engine and MCP as the connector fabric underneath it.

Semantic caching (L3 in CentRAG) stores the meaning of queries and their responses. When a new query is semantically similar to a cached one — even if the wording differs — it returns the cached answer instead of re-running the full retrieval + generation pipeline.

CentRAG's cache hierarchy: L1 (exact match) → L2 (template/near-exact) → L3 (semantic, Qdrant-backed embedding similarity). For enterprise multi-tenant use, L3 hits can reduce LLM spend by 40–60% on repeated knowledge queries.

Tools like Redis LangCache, GPTCache, or a Qdrant-backed semantic cache all work here. The key design choice: make it namespace-aware so Team A's cached answers don't bleed into Team B's context.

  • Logs: Mostly vectorless via time-bounded filters, aggregation, structured fields. Embeddings only for free-text semantic log search (edge case).
  • Documents (PDFs, Confluence, Jira): Vectorless is viable for small corpora using PageIndex (tree-structured, LLM-navigated index) or BM25 + long-context. But for large multi-tenant knowledge bases, BM25 degrades on semantic paraphrases. Dropping vectors here means a measurable quality drop.
Recommended design: "vectors as a last resort." Agentic router tries vectorless modes first; CRAG evaluator promotes to vector search only when it grades context as weak.

PageIndex is a vectorless, reasoning-based retrieval system. Instead of breaking documents into fixed-size chunks and embedding them, it builds a hierarchical tree of pages and sections using structural cues (headings, TOC, anchors).

Retrieval becomes agentic navigation: the LLM reads the top-level structure and decides which sub-sections to open next, recursing until it has enough context. No vector DB, no embedding pipeline, no chunk-size tuning required.

Trade-off: it uses more LLM calls per query (navigation cost), and it's more brittle on poorly structured documents (flat PDFs with no headings). Best suited for well-structured technical docs, runbooks, architecture documents — exactly what CentRAG serves in its KNOWLEDGE_QA path.

Because Qdrant serves two roles in CentRAG, not one:

  • L3 semantic cache backend: Stores embeddings of past queries + responses. Even a fully vectorless retrieval pipeline still benefits from semantic deduplication of repeated questions. This is low-volume, high-value usage.
  • Vector fallback retriever: When CRAG evaluates BM25/structural context as insufficient, the agentic router escalates to Qdrant. This is the safety net.

Keeping Qdrant behind a pluggable interface means you can swap it out (Weaviate, Pinecone, Chroma) without touching the orchestration layer. The goal isn't to eliminate it — it's to make it a deliberate fallback, not the default first call.

Each team is assigned a namespace. The orchestrator loads a strategy_id per namespace that controls: which retrievers run, whether PageIndex or vector is used for docs, which memory backend to use, CRAG thresholds, and L3 cache scope.

Isolation at each layer: the vector store uses namespace-scoped collection filters; the memory backend (Supermemory/Mem0/HydraDB) is tenant-keyed; the L3 semantic cache is namespace-partitioned so Team A's query hits never resolve to Team B's data.

Governance = enabling/disabling MCP servers per namespace. Need Team A to access Neptune but not Team B? Disable that MCP server for Team B's strategy_config.

Hard Technical Questions

The CRAG retrieval evaluator is an LLM-based binary/ternary classifier. After any retrieval step, it receives (query, retrieved context) and returns one of: Correct, Incorrect, or Ambiguous.

The decision routing: Correct → proceed to generation. Incorrect → discard context, rewrite query, fall back to web search or alternative retriever. Ambiguous → refine by stripping irrelevant chunks, combine with web results, or ask the user a disambiguation question.

Implementation options: (1) Use a small fine-tuned relevance scorer (e.g., a 7B model trained on CRAG benchmark data). (2) Use your production LLM with a structured prompt + JSON output. (3) Use a dedicated reranker (Cohere, cross-encoders) as a proxy for relevance scoring.

In CentRAG's Horizon 1, deploy CRAG as a read-only quality monitor (just logs scores, makes no routing decisions). Only enable routing in Horizon 2 once you've calibrated its thresholds against your internal golden sets. Miscalibrated CRAG causes more retrieval loops than necessary.

Mem0 extracts and stores key facts from conversations using an LLM extraction step. It's lightweight, open-source, and easy to self-host. Best for short-term user preference memory. Weakness: no built-in temporal decay or long-horizon reasoning.

Supermemory targets personalized, long-term AI memory with an emphasis on knowledge consolidation across sessions. It has a REST API and focuses on semantic deduplication of stored facts. Near-100% benchmark scores on personalization tasks.

HydraDB is purpose-built for agent memory at scale. It handles temporal semantics natively (memory decay, recency weighting), supports graph-like memory structures (entities, relationships, events), and is designed for multi-agent, multi-session memory. More complex to operate but best for CentRAG's COMPLEX/RESEARCH routing tiers.

Recommended: Start with Mem0 (fastest to integrate) behind a memory MCP interface. Design the interface to be swappable. Move to HydraDB when you need temporal decay and graph-aware memory for multi-hop reasoning scenarios.

The LangGraph state machine is a directed graph of nodes (functions) and edges (conditional routing). The CentRAG flow looks like this:

  • classify_query node → sets state.query_type to STRUCTURED / LOG / GRAPH / DOC_KB
  • check_cache node → checks L1/L2/L3; if hit, jumps to return_cached
  • Conditional edge: routes to retrieve_structured, retrieve_log, retrieve_graph, or retrieve_doc based on query_type
  • crag_evaluate node → grades context; sets state.crag_grade
  • Conditional edge: Correct → generate; Incorrect → retrieve_fallback; Ambiguous → refine_or_clarify
  • retrieve_memory runs in parallel with the main retrieval path, injecting long-term user/team context into the generation prompt
  • generate node → calls LLM, applies guardrails, caches result

Each node is a Python function; edges are conditional based on state fields. The key advantage: nodes can loop (CRAG can trigger multiple retrieval refinement passes) while the graph controls max iterations via a counter in state.

This is the most debated question in the space right now (2026). The honest answer is: long-context replaces naive chunk-top-k RAG in certain conditions, but not enterprise RAG at CentRAG's scale.

Where long-context wins: small-to-medium, well-bounded document sets where stuffing everything into context is affordable. Quality is genuinely comparable or better than chunk RAG in these cases.

Where RAG still dominates: large corpora across many tenants (you cannot stuff 10,000 Confluence pages into every query), real-time and frequently updated data, cost sensitivity (1M-token context = high cost per query), and multi-source synthesis where retrieval precision matters.

The pragmatic CentRAG approach: use long-context as a retrieval mode for small targeted doc sets (BM25 → pick top 3 docs → full-text into 200K context window), not as a universal replacement. CRAG evaluator decides when this mode is better than chunked retrieval.

The metrics that matter, by layer:

  • Retrieval quality: Context Recall (did we retrieve the right docs?), Context Precision (did we retrieve only relevant docs?), MRR@k
  • Generation quality: Faithfulness (is the answer grounded in retrieved context — no hallucination?), Answer Relevancy, Answer Correctness vs golden set
  • CRAG-specific: Evaluator accuracy (does CRAG's grade match human judgment?), false correction rate (CRAG triggering refinement when the original context was fine)
  • System metrics: Cache hit rate (L1/L2/L3), latency P50/P95/P99, cost per query (token spend), retrieval mode distribution (how often does each path fire?)

Tools: RAGAS framework for retrieval + faithfulness metrics. FlashRAG for benchmarking against standard datasets. Internal golden sets per team namespace for domain-specific accuracy. Dashboard per strategy_id so you can see which strategy performs best for which team.

Build the golden sets first, before tuning. Without them, every "improvement" is anecdotal.

Temporal memory decay ensures old context doesn't corrupt new answers. The problem: a team's architecture decisions from 6 months ago might be obsolete, but a naive memory system surfaces them as confidently as yesterday's decision.

Implementation options:

  • Timestamp-weighted retrieval: Score memory hits by (semantic similarity × recency score). Recency score decays exponentially: e^(-λ * age_in_days) where λ controls decay speed.
  • TTL-based eviction: Tag memory entries with an expiration. Operational facts (incident logs) expire in days; policy documents expire in months; architecture facts expire in quarters.
  • HydraDB's native approach: Stores memory as time-indexed events with built-in recency weighting during retrieval. Much simpler to configure than rolling your own.
  • Contradiction detection: On memory write, check if the new fact contradicts an existing memory. If so, mark the old one as superseded rather than just adding a new one.

CentRAG's memory MCP interface should expose: get_relevant_memory(query, namespace, max_age_days) so callers can bound the temporal window per query type.

The risks that don't exist in single-tenant RAG:

  • Cross-tenant data leakage via semantic cache: An L3 cache hit returns a cached answer — if namespace isolation is misconfigured, Team A's query could resolve to Team B's cached response. Defense: always include namespace in the cache key and filter.
  • Memory poisoning: A malicious or buggy agent writes false facts into the shared memory backend. Defense: write-only memory via trusted paths; memory writes require explicit tool calls, not open-ended generation.
  • Prompt injection via retrieved documents: A retrieved Confluence page could contain embedded instructions ("ignore previous instructions and..."). Defense: retrieved context should be passed as data, not as instructions. Use structured prompt templates that clearly delineate context from instructions.
  • Embedding inversion attacks: In theory, embeddings can be partially inverted to recover source text. Defense: don't embed PII; use namespace-scoped collections so embeddings from different tenants are never co-mixed.
The most common real-world failure: incorrect namespace propagation through the retrieval chain. Audit every retrieval node to confirm namespace is threaded through as a mandatory filter, not an optional parameter.

What to Learn Before Diving In
Tier 1 — Foundations
Must know first
RAG fundamentals
Understand the basic retrieve → augment → generate loop. Know what chunking, embeddings, and vector similarity search do and why they exist. The foundation everything else builds on.
Langchain docs · RAGFlow blog
Embeddings & vector stores
Know how dense vector representations work, why cosine similarity finds "semantically similar" text, and how Qdrant/Pinecone/Chroma index and query them. Even if you minimize vectors, you need to understand the baseline.
Qdrant docs · OpenAI embeddings guide
LangChain / LangGraph basics
CentRAG's orchestration is LangGraph. Understand: Chains, Agents, Tools, and then LangGraph's state machine model (nodes, edges, conditional routing, state schema). Spend real time on LangGraph — it's the core framework.
LangGraph docs · LangChain academy
Python async patterns
CentRAG runs concurrent retrieval paths (memory + retrieval in parallel). Know asyncio, async/await, and how LangGraph handles async nodes. Most of the performance work happens here.
Python asyncio docs
Tier 2 — Core RAG Stack
Learn in parallel
Corrective RAG (CRAG)
Read the original CRAG paper (arXiv 2401.15884). Understand the retrieval evaluator: how it classifies context, what the routing decision logic looks like, and how it was originally implemented with a lightweight fine-tuned model.
arXiv:2401.15884
Agentic RAG patterns
Study how agents plan over multiple retrieval steps: self-querying, query decomposition, iterative refinement. Understand tool-calling in OpenAI/Anthropic APIs. Build a simple 3-step agentic retrieval loop before building CentRAG's version.
FutureAGI blog · arXiv:2501.09136
BM25 + hybrid retrieval
Know how BM25 works (TF-IDF variant), why it beats dense retrieval on exact keyword matches, and how hybrid retrieval (BM25 + dense, rank-fused) outperforms either alone. Elasticsearch, OpenSearch, or Qdrant's sparse hybrid are your tools.
Elasticsearch docs · BEIR benchmark
MCP protocol
Read the MCP spec. Build a toy MCP server (Python FastMCP is the fastest path). Understand: tools vs resources vs prompts, the JSON-RPC wire format, and how LangGraph nodes call MCP tools. This unlocks all of CentRAG's external integrations.
modelcontextprotocol.io · FastMCP
Reranking
Understand cross-encoders vs bi-encoders. Cohere Rerank, BGE rerankers, and Sentence-Transformers cross-encoders all work. Reranking is often more impactful per effort than better chunking. It fits naturally after BM25 or vector retrieval.
Cohere docs · SBERT docs
Semantic caching
Understand how to embed query → store in a vector index → on new query, find nearest cached embedding → threshold check for cache hit. Study GPTCache, Redis LangCache, or build a minimal version yourself to internalize the trade-offs around staleness.
Redis LangCache docs · GPTCache GitHub
Tier 3 — Advanced Topics
After Tier 1+2 are solid
Graph RAG
Study Microsoft's GraphRAG implementation and the broader "Awesome GraphRAG" repo. Understand knowledge graph construction, Cypher/Gremlin query generation by LLMs, and subgraph extraction. Build a small graph over your own data first.
microsoft/graphrag · DEEP-PolyU/Awesome-GraphRAG
RAPTOR / hierarchical indexing
RAPTOR builds a tree of summaries from documents — embed leaf chunks AND their summaries AND their summary-of-summaries. This dramatically reduces the number of embeddings while improving long-range context retrieval. A "minimal vectors" strategy for docs.
RAPTOR paper · arXiv:2401.18059
Long-context vs RAG
Read recent benchmarks on 200K–1M context models vs chunk RAG. Understand where long-context wins (small, bounded corpora) and where it loses (cost, large multi-tenant knowledge bases). This informs CentRAG's long-context mode gating.
arXiv:2502.09891 · RAGFlow blog 2025
Memory systems (Mem0 / HydraDB)
Understand how Mem0 extracts and stores facts vs how HydraDB handles temporal decay and entity-level memory. Build a simple memory layer: write-on-generate, read-before-generate, with recency weighting. The memory MCP interface abstracts the backend.
mem0.ai · hydradb.com/blog
PageIndex / vectorless retrieval
Study PageIndex (pageindex.ai). Understand how an LLM navigates a document's structural tree without embeddings. Build a toy version: parse a PDF's headings into a tree, then write a loop where the LLM picks which node to expand next.
pageindex.ai/blog · buildfastwithai.com
RAG evaluation frameworks
Learn RAGAS (context recall, faithfulness, answer relevancy). Set up FlashRAG for benchmark runs. Build golden sets: 50–100 question/answer pairs per namespace with expert-verified answers. Without evaluation infra, you cannot tell if you're improving.
RAGAS docs · FlashRAG GitHub
Tier 4 — Ops & Scale
When building for prod
Multi-tenancy patterns
Namespace isolation in vector stores, partition-per-tenant vs collection-per-tenant trade-offs, namespace propagation through distributed systems. One bug here leaks data across teams.
LLM cost management
Token counting, cost per retrieval path, cache ROI calculation, prompt compression (LLMLingua, PromptCrunch). CentRAG's semantic cache directly reduces spend — measure it.
Observability for LLM systems
LangSmith, Langfuse, or Arize for tracing. Understand how to trace a single query across: classify → cache check → retrieve → CRAG eval → generate. Every hop needs a trace span.
LangSmith · Langfuse · Arize Phoenix
Prompt injection & RAG security
Prompt injection via retrieved docs, cross-tenant cache leakage, embedding inversion. Know the attack surface before going multi-tenant in production. Read OWASP LLM Top 10.
