Foundations

CentRAG (Centralized RAG) is an enterprise-grade retrieval-augmented generation platform designed to serve multiple teams from a single, multi-tenant, pluggable architecture. It exists because most orgs end up with many ad-hoc LLM integrations — each team rolling their own embedding pipeline, prompt layer, and connectors. CentRAG replaces that chaos with one governed platform: consistent quality, shared cost, unified observability.

The core innovation is treating retrieval as a routed, agentic decision rather than a static "always embed and search" pipeline. Different query types get different retrieval strategies — SQL for structured data, graph traversal for entity-rich domains, BM25/structural for documents — all driven by a LangGraph-based orchestrator with CRAG quality control layered on top.

The goal is "vectors as a last resort, not the default" — most queries (structured DB, logs, graph) run vectorless; the vector store is the safety net when other retrievers return poor context.

Corrective RAG (CRAG) adds a retrieval evaluator that grades context quality after any retrieval step. If the result is "Incorrect" or "Ambiguous," it triggers a correction — web search, broader window, or a disambiguation question. It is a quality guardrail that wraps any retrieval backend, not a retrieval method itself.

Agentic RAG wraps retrieval in an agent that plans and routes. Instead of always hitting the vector store, the agent decides which tools to call — SQL via MCP, log filters, graph queries, vector search — based on query type. CentRAG's SIMPLE / STANDARD / COMPLEX / RESEARCH routing tiers are an Agentic RAG pattern.

Graph RAG builds and queries a knowledge graph (Neptune / Neo4j) to handle multi-hop reasoning — "who owns service X and what incidents affected its dependencies?" It is a retrieval backend, not an orchestration layer.

These three are orthogonal and complementary. CRAG wraps any retrieval. Agentic RAG routes between retrievers. GraphRAG is one retriever among many. CentRAG uses all three simultaneously — and per 2026 benchmarks, combining all three outperforms any single approach by a significant margin.

Model Context Protocol (MCP) is an open standard by Anthropic that exposes external systems (databases, logs, ticketing tools, memory backends) as uniform JSON-RPC tool endpoints that any MCP-aware agent framework can call.

CentRAG adopts MCP because it eliminates bespoke per-system integrations. Instead of writing a custom GOS DB connector, a custom Jira connector, etc., you write one MCP server per system and any agent — including future ones — can use it. Governance becomes: "enable/disable an MCP server for a team namespace."

Think of RAG as the knowledge engine and MCP as the connector fabric underneath it. MCP also lets CentRAG evolve toward general agentic workloads (code-assist, workflow automation) without rewriting integrations.

Semantic caching (L3 in CentRAG) stores the meaning of queries and their responses. When a new query is semantically similar to a cached one — even if the wording differs — it returns the cached answer instead of re-running the full retrieval + generation pipeline.

CentRAG's cache hierarchy: L1 (exact hash match) → L2 (template / near-exact) → L3 (semantic, Qdrant-backed embedding similarity). For enterprise multi-tenant use, L3 hits can reduce LLM spend by 40–60% on repeated knowledge queries.

The key design choice: make L3 namespace-aware so Team A's cached answers don't bleed into Team B's context. The cache key must always include the namespace. Tools: Redis LangCache, GPTCache, or a Qdrant-backed semantic cache all work here.

  • Logs: Mostly vectorless via time-bounded filters, aggregation, structured fields. Embeddings only for free-text semantic log search (rare edge case).

Recommended design: "vectors as a last resort." Agentic router tries vectorless modes first; CRAG evaluator promotes to vector search only when it grades context as weak. This gets you 70–80% of queries running without embedding pipeline costs.

PageIndex is a vectorless, reasoning-based retrieval system. Instead of breaking documents into fixed-size chunks and embedding them, it builds a hierarchical tree of pages and sections using structural cues (headings, TOC, anchors).

Retrieval becomes agentic navigation: the LLM reads the top-level structure and decides which sub-sections to open next, recursing until it has enough context. No vector DB, no embedding pipeline, no chunk-size tuning required.

Trade-off: it uses more LLM calls per query (navigation cost), and is more brittle on poorly structured documents (flat PDFs with no headings). Best suited for well-structured technical docs, runbooks, and architecture documents — exactly what CentRAG serves in its KNOWLEDGE_QA path.

Because Qdrant serves two distinct roles in CentRAG, not one:

  • L3 semantic cache backend: Stores embeddings of past queries + responses. Even a fully vectorless retrieval pipeline still benefits from semantic deduplication of repeated questions. This is low-volume, high-value usage.
  • Vector fallback retriever: When CRAG evaluates BM25/structural context as insufficient, the agentic router escalates to Qdrant. This is the safety net that prevents quality regressions.

Keeping Qdrant behind a pluggable interface means you can swap it out (Weaviate, Pinecone, Chroma) without touching the orchestration layer. The goal isn't to eliminate it — it's to make it a deliberate fallback, not the default first call.

Each team is assigned a namespace. The orchestrator loads a strategy_id per namespace that controls: which retrievers run, whether PageIndex or vector is used for docs, which memory backend to use, CRAG thresholds, and L3 cache scope.

Isolation at each layer: the vector store uses namespace-scoped collection filters; the memory backend (Supermemory/Mem0/HydraDB) is tenant-keyed; the L3 semantic cache is namespace-partitioned so Team A's query hits never resolve to Team B's data.

Governance = enabling/disabling MCP servers per namespace. Need Team A to access Neptune but not Team B? Disable that MCP server for Team B's strategy_config. This makes access control declarative and auditable.

The most common real-world failure: incorrect namespace propagation through the retrieval chain. Audit every retrieval node to confirm namespace is threaded as a mandatory filter, not an optional parameter.

These are CentRAG's four query complexity tiers, each triggering a different retrieval + reasoning strategy:

  • SIMPLE: Single-retriever path. Usually SQL or log filter via MCP. No CRAG refinement loop. Lowest latency and cost.
  • STANDARD: One or two retrievers, single CRAG pass. Covers most structured + known-doc queries.
  • COMPLEX: Multi-retriever (e.g. graph + docs + memory). Multiple CRAG passes allowed. Memory MCP retrieval injected. Used for cross-domain, multi-hop questions.
  • RESEARCH: Full agentic loop — planning, iterative retrieval, web search fallback, multi-step reasoning. Highest accuracy but also highest cost and latency. Reserved for genuinely hard queries where a simple answer is known to be insufficient.

The router makes this classification before any retrieval happens, based on query features (question length, entity count, keyword signals, namespace-specific patterns). You can override per-namespace defaults in the strategy_config.

Hard Technical Questions

The CRAG retrieval evaluator is an LLM-based binary/ternary classifier. After any retrieval step, it receives (query, retrieved_context) and returns one of: Correct, Incorrect, or Ambiguous.

Decision routing: Correct → proceed to generation. Incorrect → discard context, rewrite query, fall back to web search or alternative retriever. Ambiguous → refine by stripping irrelevant chunks, combine with web results, or ask the user a disambiguation question.

Implementation options: (1) Use a small fine-tuned relevance scorer (7B model trained on CRAG benchmark data). (2) Use your production LLM with a structured prompt + JSON output for the grade. (3) Use a dedicated reranker (Cohere, cross-encoders) as a proxy for relevance scoring.

In Horizon 1, deploy CRAG as a read-only quality monitor (logs scores, makes zero routing decisions). Only enable routing in Horizon 2 once thresholds are calibrated against your internal golden sets. Miscalibrated CRAG causes more retrieval loops than necessary and increases latency significantly.

Mem0 extracts and stores key facts from conversations using an LLM extraction step. Lightweight, open-source, easy to self-host. Best for short-term user preference memory. Weakness: no built-in temporal decay or long-horizon reasoning across sessions.

Supermemory targets personalized, long-term AI memory with an emphasis on knowledge consolidation across sessions. REST API, semantic deduplication of stored facts, near-100% benchmark scores on personalization tasks. Good for user-facing assistants where personalization matters.

HydraDB is purpose-built for agent memory at scale. It handles temporal semantics natively (memory decay, recency weighting), supports graph-like memory structures (entities, relationships, events), and is designed for multi-agent, multi-session memory. More complex to operate but best for CentRAG's COMPLEX/RESEARCH routing tiers where past architectural decisions affect current answers.

Recommended path: Start with Mem0 (fastest to integrate) behind a memory MCP interface. Design the interface to be swappable. Migrate to HydraDB in H3 when you need temporal decay and graph-aware memory for multi-hop reasoning scenarios. Never couple the orchestrator directly to a memory library — always go through the MCP interface.

The LangGraph state machine is a directed graph of nodes (Python functions) and edges (conditional routing). The CentRAG flow looks like this:

  • classify_query → sets state.query_type to STRUCTURED / LOG / GRAPH / DOC_KB
  • check_cache → checks L1/L2/L3; if hit, jumps to return_cached
  • Conditional edge: routes to retrieve_structured, retrieve_log, retrieve_graph, or retrieve_doc based on query_type
  • crag_evaluate → grades context; sets state.crag_grade
  • Conditional edge: Correct → generate; Incorrect → retrieve_fallback; Ambiguous → refine_or_clarify
  • retrieve_memory runs in parallel with the main retrieval path, injecting long-term user/team context into the generation prompt
  • generate → calls LLM, applies guardrails, caches result

Each node is a Python function; edges are conditional based on state fields. Nodes can loop (CRAG can trigger multiple retrieval refinement passes) while the graph controls max iterations via a retry_count in state. LangGraph's add_conditional_edges() maps state values to node names — this is what makes the routing declarative and testable.

This is the most debated question in the space right now (2026). The honest answer is: long-context replaces naive chunk-top-k RAG in certain conditions, but not enterprise RAG at CentRAG's scale.

Where long-context wins: small-to-medium, well-bounded document sets where stuffing everything into context is affordable. Quality is genuinely comparable or better than chunk RAG in these cases (benchmarks confirm this for corpora under ~500K tokens).

Where RAG still dominates: large corpora across many tenants (you cannot stuff 10,000 Confluence pages into every query), real-time and frequently updated data, cost sensitivity (1M-token context at current pricing = prohibitive per-query cost), and multi-source synthesis where retrieval precision matters.

The pragmatic CentRAG approach: use long-context as a retrieval mode for small targeted doc sets (BM25 → pick top 3 docs → full-text into 200K context window), not as a universal replacement. CRAG evaluator decides when this mode is better than chunked retrieval. This hybrid is already a recognized best practice in 2026.

The metrics that matter, by layer:

  • Retrieval quality: Context Recall (did we retrieve the right docs?), Context Precision (did we retrieve only relevant docs?), MRR@k
  • Generation quality: Faithfulness (is the answer grounded in retrieved context — no hallucination?), Answer Relevancy, Answer Correctness vs golden set
  • CRAG-specific: Evaluator accuracy (does CRAG's grade match human judgment?), false correction rate (CRAG triggering refinement when the original context was fine)
  • System metrics: Cache hit rate (L1/L2/L3 separately), latency P50/P95/P99, cost per query (token spend), retrieval mode distribution (how often each path fires)

Tools: RAGAS framework for retrieval + faithfulness metrics. FlashRAG for benchmarking against standard datasets. Internal golden sets per team namespace for domain-specific accuracy. Dashboard per strategy_id so you can see which strategy performs best for which team.

Build the golden sets first, before tuning. Without them, every "improvement" is anecdotal. Target 50–100 Q&A pairs per namespace with expert-verified answers.

Temporal memory decay ensures old context doesn't corrupt new answers. The problem: a team's architecture decisions from 6 months ago might be obsolete, but a naive memory system surfaces them as confidently as yesterday's decision.

Implementation options:

  • Timestamp-weighted retrieval: Score memory hits by semantic_similarity × recency_score. Recency score decays exponentially: e^(-λ × age_in_days) where λ controls decay speed.
  • TTL-based eviction: Tag memory entries with an expiration. Operational facts (incident logs) expire in days; policy documents in months; architecture facts in quarters.
  • HydraDB's native approach: Stores memory as time-indexed events with built-in recency weighting during retrieval. Much simpler to configure than rolling your own.
  • Contradiction detection: On memory write, check if the new fact contradicts an existing memory. If so, mark the old one as superseded rather than adding both.

CentRAG's memory MCP interface should expose: get_relevant_memory(query, namespace, max_age_days) so callers can bound the temporal window per query type.

The risks that don't exist in single-tenant RAG:

  • Cross-tenant data leakage via semantic cache: An L3 cache hit returns a cached answer — if namespace isolation is misconfigured, Team A's query could resolve to Team B's cached response. Defense: always include namespace in the cache key and filter.
  • Memory poisoning: A malicious or buggy agent writes false facts into the shared memory backend. Defense: write-only memory via trusted paths; memory writes require explicit tool calls, not open-ended generation.
  • Prompt injection via retrieved documents: A retrieved Confluence page could contain embedded instructions ("ignore previous instructions and..."). Defense: retrieved context should be passed as data, not as instructions. Use structured prompt templates that clearly delineate context from instructions.
  • Embedding inversion attacks: In theory, embeddings can be partially inverted to recover source text. Defense: don't embed PII; use namespace-scoped collections so embeddings from different tenants are never co-mixed.
The most common real-world failure: incorrect namespace propagation through the retrieval chain. Audit every retrieval node to confirm namespace is threaded as a mandatory filter, not an optional parameter. Read OWASP LLM Top 10 before multi-tenant production launch.

RAPTOR (Recursive Abstractive Processing for Tree-Organized Retrieval) builds a hierarchical tree of summaries from documents: it embeds leaf chunks AND their summaries AND summaries-of-summaries. This dramatically reduces the number of embeddings required while improving long-range context retrieval.

When to use in CentRAG: When you have large, well-structured documents (architectural runbooks, long policy documents) where a user might ask cross-section questions that require understanding multiple parts of the document. RAPTOR lets you answer "what is the overall philosophy of our deployment strategy?" without retrieving specific chunks — the summary node contains that abstraction.

When NOT to use: Small corpora (PageIndex is better), highly factual/exact-answer queries (chunk retrieval is more precise), and structured data (use SQL). RAPTOR adds an indexing overhead cost and complexity that isn't worth it for simple lookup queries.

Think of RAPTOR as a "minimal vectors" strategy: you embed much less content (summaries are smaller than all raw chunks combined) while maintaining broad semantic coverage. It fits cleanly into CentRAG's goal of minimizing embedding maintenance overhead.

CentRAG's GraphRAG path targets entity-rich, relationship-heavy domains: service ownership, incident graphs, dependency graphs, and org hierarchies. The build process:

  • Entity extraction: An LLM pass over incident reports, service catalogs, and runbooks extracts entities (services, teams, deployments, error codes) and relationships (depends_on, owned_by, caused_by).
  • Graph store: Neptune (or Neo4j) stores these as nodes and edges with properties (timestamps, severity, version).
  • Retrieval: For a GRAPH_QA query, the LLM translates the natural language question into Cypher/Gremlin. The resulting subgraph (a few nodes + edges) is extracted and converted to text. This text is fused with any document context for generation.

The key design decision: the GraphRAG retriever is exposed via MCP so the LangGraph orchestrator calls it like any other tool. It doesn't need special orchestration — it's just another retrieval option in the router's toolkit.

Best domains for GraphRAG in CentRAG: incident root cause analysis ("what services depend on the failing service?"), ownership queries ("who is responsible for this alert?"), and multi-hop KB questions ("what policies govern this team's data handling?").

LangGraph's built-in checkpointing serializes the full graph state (including messages, retrieved docs, CRAG grades, retry counts) to a persistent store (Postgres, Redis, or SQLite) at each node transition. This enables:

  • Resumability: If a RESEARCH-tier query times out or the LLM provider is temporarily unavailable, the orchestrator can resume from the last checkpoint rather than starting over. Critical for multi-step, multi-minute research flows.
  • Human-in-the-loop: The graph can pause at a clarify node, persist state, return a question to the user, and resume when the user responds — even if that response arrives 10 minutes later.
  • Debugging: LangSmith and LangGraph Studio can replay a specific checkpoint sequence to diagnose why a particular CRAG routing decision was made.

Implementation: use MemorySaver for development, SqliteSaver or PostgresSaver for production. Pass the thread_id (your trace_id) as the checkpointing key so each unique query flow has its own checkpoint chain.

Per source type, the realistic vectorless picture is:

  • GOS DB / Athena / DynamoDB: 100% vectorless. Agent uses schema introspection via MCP + SQL/aggregation queries. The LLM explains the result. No chunking, no embeddings.
  • Logs: ~90% vectorless. Primary retrieval via time bounds, service filters, error class, correlation IDs. Aggregated views (hourly error counts, DAG failure summaries) produced via SQL/OLAP. Embeddings only for free-text semantic search on log messages (edge case).
  • Confluence / Jira / PDFs: 60–70% vectorless is achievable using BM25 page-level index + PageIndex structural navigation for well-structured docs. The remaining 30–40% (semantically phrased, long-tail questions on large corpora) still needs vector fallback to avoid quality regressions.
BM25 struggles with semantic paraphrases — "salary bands" vs "compensation tiers" will fail to match. If your users ask in business language while docs are written in technical language, expect vector fallback to trigger frequently. Calibrate your CRAG threshold accordingly.

What to Learn Before Diving In
Tier 1 — Foundations · Must know first
RAG fundamentals
Understand the basic retrieve → augment → generate loop. Know what chunking, embeddings, and vector similarity search do and why they exist. The foundation everything else builds on — even if CentRAG minimizes them, you need to know the baseline to know when to deviate.
LangChain docs · RAGFlow blog 2025
Embeddings + vector stores
Know how dense vector representations work, why cosine similarity finds "semantically similar" text, and how Qdrant/Pinecone/Chroma index and query them. Even if you minimize vectors, you need to understand the baseline to make informed decisions about when to deviate.
Qdrant docs · OpenAI embeddings guide
LangChain + LangGraph basics
CentRAG's orchestration is LangGraph. Understand: Chains, Agents, Tools, and then LangGraph's state machine model — nodes, edges, conditional routing, TypedDict state schema. Spend real time on LangGraph; it's the core framework. Build a 3-node flow before touching CentRAG.
LangGraph docs · LangChain Academy
Python async patterns
CentRAG runs concurrent retrieval paths (memory + retrieval in parallel). Know asyncio, async/await, and how LangGraph handles async nodes. Most of the performance work happens here — misusing sync code in async contexts causes hard-to-debug latency spikes.
Python asyncio docs
Basic LLM API usage
Know how to make structured calls to Anthropic/OpenAI APIs: tool calling, structured JSON outputs, system prompts, multi-turn conversations. CentRAG uses tool calling heavily — both for the LLM-as-router pattern and for MCP tool dispatch.
Anthropic docs · OpenAI API reference
Tier 2 — Core RAG Stack · Learn in parallel with Tier 1
Corrective RAG (CRAG)
Read the original CRAG paper (arXiv 2401.15884). Understand the retrieval evaluator: how it classifies context, what the routing decision logic looks like, and how it was originally implemented with a lightweight fine-tuned model. Then study the LangChain CRAG cookbook implementation.
arXiv:2401.15884 · LangChain CRAG cookbook
Agentic RAG patterns
Study how agents plan over multiple retrieval steps: self-querying, query decomposition, iterative refinement. Understand tool-calling in Anthropic/OpenAI APIs. Build a simple 3-step agentic retrieval loop with LangGraph before building CentRAG's version.
arXiv:2501.09136 · FutureAGI blog
BM25 + hybrid retrieval
Know how BM25 works (TF-IDF variant), why it beats dense retrieval on exact keyword matches, and how hybrid retrieval (BM25 + dense, rank-fused) outperforms either alone. Elasticsearch, OpenSearch, or Qdrant's sparse hybrid are your tools. This is what makes vectorless modes viable.
Elasticsearch docs · BEIR benchmark
MCP protocol
Read the MCP spec from modelcontextprotocol.io. Build a toy MCP server using Python FastMCP. Understand: tools vs resources vs prompts, the JSON-RPC wire format, and how LangGraph nodes call MCP tools. This unlocks all of CentRAG's external system integrations.
modelcontextprotocol.io · FastMCP
Reranking
Understand cross-encoders vs bi-encoders. Cohere Rerank, BGE rerankers, and Sentence-Transformers cross-encoders all work. Reranking is often more impactful per unit of effort than better chunking. It fits naturally after BM25 or vector retrieval as a quality booster before CRAG evaluation.
Cohere docs · SBERT docs
Semantic caching
Understand how to embed a query → store in a vector index → on new query, find nearest cached embedding → threshold check for cache hit. Study GPTCache, Redis LangCache, or build a minimal version to internalize the trade-offs around staleness and namespace isolation.
Redis LangCache docs · GPTCache GitHub
Tier 3 — Advanced Topics · After Tier 1 + 2 are solid
Graph RAG
Study Microsoft's GraphRAG implementation and the "Awesome GraphRAG" repo. Understand knowledge graph construction, Cypher/Gremlin query generation by LLMs, and subgraph extraction. Build a small graph over your own incident data first before tackling Neptune integration.
microsoft/graphrag · DEEP-PolyU/Awesome-GraphRAG
RAPTOR / hierarchical indexing
RAPTOR builds a tree of summaries — embed leaf chunks AND their summaries AND summary-of-summaries. This reduces the number of embeddings while improving long-range context retrieval. Study the RAPTOR paper (arXiv:2401.18059) and build a small toy version over a multi-section doc.
RAPTOR paper · arXiv:2401.18059
Long-context vs RAG
Read recent benchmarks on 200K–1M context models vs chunk RAG (RAGFlow blog 2025, arXiv:2502.09891). Understand where long-context wins (small, bounded corpora) and where it loses (cost, large multi-tenant knowledge bases). This informs CentRAG's long-context mode gating decisions.
arXiv:2502.09891 · RAGFlow blog 2025
Memory systems (Mem0 / HydraDB)
Understand how Mem0 extracts and stores facts vs how HydraDB handles temporal decay and entity-level memory. Build a simple memory layer: write-on-generate, read-before-generate, with recency weighting. The memory MCP interface abstracts the backend — understand the interface before the implementation.
mem0.ai · hydradb.com/blog
PageIndex / vectorless retrieval
Study PageIndex (pageindex.ai). Understand how an LLM navigates a document's structural tree without embeddings. Build a toy version: parse a PDF's headings into a tree, write a loop where the LLM picks which node to expand next. This is the core of CentRAG's structural doc retriever.
pageindex.ai/blog · buildfastwithai.com
RAG evaluation frameworks
Learn RAGAS (context recall, faithfulness, answer relevancy, answer correctness). Set up FlashRAG for benchmark runs. Build golden sets: 50–100 Q&A pairs per namespace with expert-verified answers. Without evaluation infrastructure, you cannot tell if you're improving. This is non-negotiable for H1.
RAGAS docs · FlashRAG GitHub
Self-RAG + Adaptive RAG
Self-RAG trains a model to decide when to retrieve, what to retrieve, and how to evaluate its own output. Adaptive RAG adjusts retrieval complexity based on query difficulty. Both are related to CRAG but add self-reflection loops. Study the papers, then understand how CentRAG's CRAG + Agentic routing approximates these patterns without fine-tuning.
Self-RAG paper · Adaptive RAG · LangGraph tutorials

Prompt injection via retrieved docs, cross-tenant cache leakage, embedding inversion, memory poisoning. Know the attack surface before going multi-tenant in production. Read OWASP LLM Top 10. These risks are unique to multi-tenant RAG and often overlooked until they cause an incident.

LangGraph checkpointing + HITL
Understand LangGraph's MemorySaver, SqliteSaver, and PostgresSaver. Know how to pause a graph at a clarify node, persist state, and resume when a user responds. Human-in-the-loop (HITL) is essential for CentRAG's RESEARCH tier where ambiguous queries need user input before proceeding.

Bandit algorithms for strategy selection
Understand ε-greedy and Thompson Sampling for multi-armed bandits. In H4, CentRAG uses bandits to auto-promote better retrieval strategies per namespace. You don't need deep math — understand the explore/exploit trade-off and how to implement a simple version for strategy routing.
